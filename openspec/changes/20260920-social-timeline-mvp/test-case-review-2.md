## 四、建议级问题

1. **test-cases.md:TC078 — 越界笔数计数标注错误**
   - 失败场景：入参声明"userCount=0/100001、avgFriendsPerUser=-1/501、extraTagsPerUser=21、postCount=10001（8 笔）"——实际列出 6 笔越界组合，"8 笔"计数与实列不符；预期本身正确（均 1040，与 api.md 接口11 四参数范围边界逐项核对无误）。
   - 攻击维度：清单 3（预期可核对性——统计口径笔误）
   - 建议：计数改 6 笔，或补列 avgFriendsPerUser/userCount 另一侧（当前已双测，无需补）。

2. **test-cases.md:TC074 — 统计容差数值未定义且未标软校验**
   - 失败场景："friendship 表记录 ≈1000（±抖动容差）"未给数值（design §5.5 抖动 ±3 下 100 用户记录数 3σ≈±56 条），且覆盖核对仅将 TC075/079/136 列为软校验——TC074 若被 tester 按硬断言实现，容差取值含糊可致间歇红灯。
   - 攻击维度：清单 3（预期可核对性）
   - 建议：补容差数值（如 ±15%）或纳入"观测软校验不计红灯"标注；确定性三断言（对称/无自环/无重复）保持硬断言。

3. **test-cases.md:入口11 参数维度 — 轻量合法边界声明与落地不对齐**
   - 失败场景：维度表声明"avgFriendsPerUser 边界 0、500 / userCount 边界 1、100000 / extraTagsPerUser 边界 0、20 / postCount 边界 0、10000"，但业务场景仅覆盖缺省值与越界侧（-1/501→1040），合法边界值（avg=0/500 等）无落地用例。性质为数值等价类代表点缺失（与 B4 场景二的语义分叉缺口不同：0 与 10 走同一生成逻辑，无行为分叉；avg=0 的空集读侧行为已由 TC129 部分覆盖），且 100000/10000 上界与 R10（10 万级属三期）立场一致可省。
   - 攻击维度：清单 1（参数维度声明与落地缺口——数值等价类）
   - 建议：补 1 笔 avgFriendsPerUser=0 轻量用例，或维度表标注"上界类边界按 R10 省略留痕"。

4. **test-cases.md:TC128 — "毫秒错开保证同序"措辞与 schema 精度不符**
   - 失败场景：post.created_stime 为 DATETIME（秒精度，无 (3)，sql.md §1），直插毫秒会被截断——"毫秒错开"无法按字面落地；实际 (created_stime, id) 复合键在任何插法下均产生确定全序，TC128 推演与"游标严格小于"断言不受影响（基线 t=10:00:00.000 的毫秒段恒 000，TC127 毫秒段断言同样自洽）。
   - 攻击维度：清单 3（可执行性——tester 直插时会产生的措辞困惑）
   - 建议：措辞改"秒级错开或同秒依赖 id 倒序保证全序"。

5. **附注（非用例缺陷，api.md 派生文档勘误）— §1.6 错误码汇总表 1011 行触发接口含"15"，与接口15 明细异常码表（仅 1001/1002/1003，canView 过滤为静默不报错）不一致**；test-cases 的 TC120/121 按明细表语义（列表过滤而非 1011）编写，用例侧无缺陷。建议主 agent 转设计侧做 §1.6 行级勘误（同裁决 1/2 的派生文档同步处理模式）。
