# 6 类需求拆解框架（领域先验知识库）

> 本文档是 `requirement-classifier` subagent 的对照基准。
> 读完需求文档后，先判断属于哪一类，再用对应框架作为审查基准。

## 使用方法

1. 识别需求类型（可复合）
2. 加载对应的"标准拆解框架"
3. 用框架列出"该类需求应该有但文档可能缺的前提条件"
4. 为 4 个角色生成专属检查提示

---

## 1. AI / 自动化识别类

**识别信号**：识别、覆盖率、准确率、Bad Case、模型、AI、智能、自动化

### 标准拆解框架（正确做法下必须有的前提）

- **输入空间定义**：覆盖哪些输入类型？（如：机型 × 部件大类，不是"所有工单"）
- **输出规则穷举**：每种输入对应的正确输出是什么？边界情况如何处理？
- **Bad Case 分类**：历史错误分几类？各占比多少？不同类别的处理难度是否一样？
- **指标推导链**：SPEC 范围 → 历史数据批量测试 → 覆盖率天花板 → 基于测试结论定上线指标
- **降级方案**：AI 识别失败或置信度低时，交互如何设计？会不会增加用户负担？
- **测试用例对应性**：用例是否按照 Bad Case 分类设计，数量是否足够代表各类别？

### 常见缺陷信号

- ❗ 目标是拍的（没有基于历史数据测算）
- ❗ SPEC 用"全量工单"而非分类界定
- ❗ 测试用例是随机抽样而非按类别设计

### 4 角色专属检查提示

| 角色 | 加码维度 |
|------|---------|
| product_director | 审查 SPEC 是否定义；量化目标的推导逻辑是否清晰 |
| tech_leader | 审查降级方案（AI 失败兜底）；Bad Case 是否分类 |
| frontend_dev | 审查 AI 置信度低时的交互降级；识别失败时的用户提示 |
| qa_engineer | 审查测试用例是否覆盖 SPEC 矩阵交叉点（非数量凑够） |

## 2. 数据治理 / 投诉处理类

**识别信号**：多通路、分类汇总、责任判定、来源、字段口径、投诉、CEC、CCC、MOT

### 标准拆解框架

- **来源 × 通路矩阵**：数据从哪几个来源进来？每条通路的字段结构是否一致？
- **阶段拆分**：处理链路分几个阶段？（关键信息识别 → 分类汇总 → 分析输出）
- **责任判定规则**：判定标准是什么？有没有灰色地带？误判的处罚成本是什么？
- **准确率基线的含义**：60% 准确率，是哪个阶段的哪类判断？分子分母各是什么？
- **Road Map 顺序逻辑**：通路 × 阶段矩阵中，哪个格子最痛？优先从这里启动

### 常见缺陷信号

- ❗ 把多通路、多阶段的问题当成一个整体需求
- ❗ 准确率目标没有说明是哪个环节的哪类判断
- ❗ 没有定义责任判定的灰色地带处理规则

### 4 角色专属检查提示

| 角色 | 加码维度 |
|------|---------|
| product_director | 审查多通路每条的痛点权重；准确率目标的分子分母 |
| tech_leader | 审查通路 × 阶段矩阵；多通路字段一致性 |
| frontend_dev | 审查分类汇总的展示逻辑；多通路数据的统一展示 |
| qa_engineer | 审查通路 × 阶段的覆盖测试；灰色地带的测试用例 |

---

## 3. 工单流程 / 换件操作类

**识别信号**：操作链路、编码规则、错误率、工单、流程节点、换件、返件

### 标准拆解框架

- **操作链路完整描述**：当前的完整作业链路是什么？出错发生在哪个节点？
- **错误类型分类**：错误分几种？（人工记忆错误 / 系统未校验 / 规则本身有歧义）各占比多少？
- **规则复杂度评估**：编码规则是结构化的（可以用规则引擎）还是模糊的（需要语义理解）？
- **系统干预时机**：在工单的哪个步骤介入？介入太晚会不会改不了？
- **容错设计**：识别错误时如何提示？工程师是否有二次确认机会？

### 常见缺陷信号

- ❗ 把"人工记错"和"系统没校验"混为一谈（解法完全不同）
- ❗ 没有说明规则的结构化程度就直接选 AI 方案
- ❗ 没有设计识别失败时的交互降级

### 4 角色专属检查提示

| 角色 | 加码维度 |
|------|---------|
| product_director | 审查错误类型的痛点权重；不做的人工兜底成本 |
| tech_leader | 审查规则复杂度（结构化 vs 模糊）；干预时机合理性 |
| frontend_dev | 审查错误识别的二次确认交互；工程师的容错路径 |
| qa_engineer | 审查错误分类的覆盖测试；规则边界条件测试 |

---

## 4. 提效 / 流程自动化类

**识别信号**：耗时、效率提升、单均、自动化、瓶颈、提效、节省

### 标准拆解框架

- **当前流程的完整耗时拆解**：每个步骤各花多少时间？瓶颈在哪一步？
- **自动化边界**：哪些步骤可以自动化？哪些必须人工判断？
- **成本转移检查**：提效是真正减少了工作量，还是把成本转移给了其他岗位/其他时间？
- **单均数据**：总时间 / 总量 = 单均时间，才能计算 AI 上线后的实际节省

### 常见缺陷信号

- ❗ 只给总时间不给单均时间，无法计算效率提升空间
- ❗ 提效实际上是把工作转移给了其他人

### 4 角色专属检查提示

| 角色 | 加码维度 |
|------|---------|
| product_director | 审查 ROI 测算逻辑；成本转移是否识别 |
| tech_leader | 审查自动化边界的合理性；瓶颈步骤的可行性 |
| frontend_dev | 审查自动化失败时的回退路径 |
| qa_engineer | 审查效率指标的量化方法；采样策略 |

## 5. 管理看板 / 报表类

**识别信号**：看板、报表、决策、可视化、统计、监控、Dashboard

### 标准拆解框架

- **服务什么决策**：谁看？看完做什么决策？决策频率多高？
- **不用系统现在怎么判断**：当前的替代方案是什么？替代方案的主要缺陷是什么？
- **数据来源可信度**：报表的数据从哪来？口径统一吗？

### 常见缺陷信号

- ❗ 决策频率不清晰，无法判断报表价值
- ❗ 数据口径不统一，导致报表不可信

### 4 角色专属检查提示

| 角色 | 加码维度 |
|------|---------|
| product_director | 审查决策价值；与现有替代方案的差异 |
| tech_leader | 审查数据来源；口径统一性；数据更新频率 |
| frontend_dev | 审查可视化设计；关键指标的视觉权重 |
| qa_engineer | 审查数据准确性验证方法；口径测试 |

## 6. 数据产品 / BI 类（重点）

**识别信号**：指标、看板、报表、数据 API、画像、标签、推荐、数据资产、数据中台、数仓、血缘、埋点、BI、Dashboard、数据治理、元数据、指标平台、T+1、数据更新

> 区别于"管理看板/报表类"：数据产品类是**数据本身就是产品**（多角色消费、链路长、SLA 敏感），
> 管理看板类是**用数据辅助决策**（单一决策者、链路短）。

### 子类型（识别时进一步细分）

| 子类型 | 特征 | 关键关注 |
|-------|------|---------|
| 数据看板 / BI | Tableau/PowerBI/Superset | 可视化、交互、性能 |
| 数据 API 服务 | 对外提供数据接口 | QPS、并发、Schema 稳定性 |
| 指标平台 | 统一指标定义和管理 | 指标治理、口径唯一 |
| 用户画像 / 标签 | 基于行为数据生成画像 | 标签计算、人群圈选 |
| 推荐 / 排序系统 | 基于数据做推荐 | 召回、排序、AB 测试 |
| 数据治理 | 数据质量、血缘、元数据 | 治理规则、监控告警 |
| 实时数据服务 | 流式数据服务 | 延迟、吞吐、容错 |

### 标准拆解框架（9 大前提条件）

- **指标定义层**：每个指标有唯一定义 + 计算公式 + 业务口径 + 负责人；同名指标跨部门口径一致
- **数据源 × 链路矩阵**：数据从哪几个源来（具体表名，不是"数仓"）？经过哪些加工环节（ODS→DWD→DWS→ADS）？
- **更新频率 × 时效性**：T+1 / 小时 / 实时？业务能容忍的最大延迟？不同频率的工程量差异
- **数据质量 SLA**：准确率（与源数据对比）、完整性（缺失率）、及时性（SLA 时间）、一致性（跨报表）
- **下游影响评估（血缘）**：底表一动影响多少下游？血缘梳理是否完成？变更通知机制
- **权限 × 安全**：行级/列级权限、敏感字段脱敏、合规要求（GDPR/个保法）、数据等级分类
- **历史数据策略**：回算方案（多久、怎么算）、保留周期、归档策略、冷热数据分层
- **性能 SLA**：查询响应时间（P50/P95/P99）、并发能力、数据量级、分页/聚合策略
- **消费场景对齐**：谁用（角色）、何时用（场景）、用什么决策（动作）、决策频率

### 常见缺陷信号

- ❗ 指标定义模糊（"GMV"不分下单/支付/退款后；"活跃"无明确口径）
- ❗ 数据源未明确（"从数仓取"而非具体表名 + 链路）
- ❗ 更新频率未约定（实时 vs T+1 成本估算差 10 倍）
- ❗ 数据质量验收方法未定义（"准确"无量化标准 + 无抽样方法）
- ❗ 下游影响未评估（改动一处底表影响 50 张报表）
- ❗ 历史数据策略缺失（上线后回算 1 年数据要 1 个月）
- ❗ 性能要求拍脑袋（"快速响应"无具体毫秒数）
- ❗ 权限合规未考虑（行/列权限、脱敏、个保法）
- ❗ 消费场景未对齐（上线后没人看 / 看不懂）

### 4 角色专属检查提示

| 角色 | 加码维度 |
|------|---------|
| product_director | 审查每个指标服务的业务决策、决策频率；数据 ROI；现有替代方案为何不够；下线标准 |
| tech_leader | 审查数据源 × 链路矩阵、更新频率成本、血缘影响、质量 SLA、性能 SLA、存储计算成本 |
| frontend_dev | 审查大数据量加载（分页/虚拟滚动）、空数据状态、导出能力、筛选钻取、可视化选型、缓存策略 |
| qa_engineer | 审查数据准确性抽样校验、口径一致性、数据完整性（缺失/重复/异常）、性能压测、血缘回归、数据监控告警 |

## 7. 风控 / 合规类

**识别信号**：风险、合规、兜底、审计、权限控制、风控、违规

### 标准拆解框架

- **风险分布**：高频低损还是低频高损？历史发生频次？
- **责任主体**：谁来承担风险后果？
- **当前兜底方案**：现在靠谁/靠什么来防止风险？兜底方案的漏洞在哪？

### 常见缺陷信号

- ❗ 风险分布未量化，无法判断严重性
- ❗ 兜底方案漏洞未识别，新方案可能引入新风险

### 4 角色专属检查提示

| 角色 | 加码维度 |
|------|---------|
| product_director | 审查风险量级；不做的影响 |
| tech_leader | 审查兜底方案；新方案引入的新风险 |
| frontend_dev | 审查风险提示的交互；用户告知同意流 |
| qa_engineer | 审查风险场景的测试覆盖；合规边界测试 |

## 复合类型处理

如果需求涉及多个类型（如 `AI识别 + 数据治理`）：

1. **primary**：业务本质最贴近的类型
2. **secondary**：次要类型（可空）
3. **拆解框架**：以 primary 为主，融合 secondary 的关键维度
4. **4 角色提示**：合并两个类型的加码维度，去重后取最重要的 2-3 条

## 低置信度场景

如果信号不显著：

1. 选最贴近的 primary，但 confidence 标"低"
2. 标注"复合/不明确"
3. 4 角色提示都标"按通用清单审查，本类型无明显特征"
4. 拆解框架留空，common_defects 标"无明确信号"
